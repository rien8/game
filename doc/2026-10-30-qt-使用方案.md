# Qt 使用方案

这份文档回答两件事：这套 GUI 后面还会大改，**Qt 该怎么用**；以及**迭代一圈
要花多少时间**，哪些地方值得先投。

结论先说：**留在 QWidget，主干不迁 Qt Quick；面板层搬 `.ui`（Designer），
重绘视图留在 C++/QPainter；把美术资产改成磁盘热重载；把启动流程做成一
条命令能进可操作状态。** QML 留作触发式备选，触发条件写在下面。

## 现状：已经做对的三件事

1. **模拟层与界面层是分开的。** `demo_scenario`（场景配置）与
   `gui::Simulation`（快照）都不依赖 Qt，`sim` 与 `demo_gui` 跑同一个世界。
   这是整个项目最重要的一条地基，界面随便改都不会动到模拟。
2. **绘制层是纯读快照的。** `paintEvent` 只画 `refresh()` 取好的数据，
   不在绘制里遍历实体。
3. **素材进包。** `qt_add_resources` 把精灵打成 `:/assets/...`，不依赖运行
   目录。

## 实测：迭代一圈要花多久

本机实测（Debug、clang++、Unix Makefiles、Qt 6.12 msvc2022_64）：

| 动作 | 耗时 | 说明 |
| --- | --- | --- |
| 改 `src/gui/views.cpp` 后重建 | 4.0s | 编译 + 链接 |
| 只改一张 PNG 后重建 | 1.4s | rcc 重跑 + 链接 |
| 空跑构建 | 1.1s | |
| 启动到窗口出现 | 1.3s | |
| 世界生成 256×256 | 1.85s | 启动与「重开」各阻塞一次 |
| `sim` 跑一季 | 0.95s | |

**瓶颈不在编译。** 一次「改代码 → 看到效果」的完整循环是 4s 编译 + 1.3s 启动
+ 1.85s 世界生成 + 手点弹窗选人 ≈ 10s，而其中只有 4s 是编译。

真正的摩擦有三处，都跟"界面要大改"直接相关：

1. **界面没有可拖拽的层。** `main.cpp` 里主窗口、四个分组面板、选项卡全
   是手写的 `QVBoxLayout`/`QFormLayout` 加 `new`。加一个面板 = 改 C++ =
   重新编译 + 重启 + 重新点一遍弹窗。面板一多，这块会先垮。
2. **美术迭代要重链。** 精灵在 qrc 里，改一张 PNG 虽只要 1.4s，但它是
   "改资源"被当成了"改代码"。
3. **每次启动都要重新走一遍世界生成 + 手动选人。** 想复现"第 90 季、玩家
   在东南角"这个状态，只能盯着它跑。

另外还有一处**结构性泄漏**：`views.cpp` 直接 include 了 ECS 头文件，直接调
`sim_.entities()` 遍历实体、直接读 `sim_.environment()` 的格网。GUI 摸到了
ECS 内部，界面每加一个字段都要回去改 ECS 侧的读法。

## 推荐方案

### 分层

```
模拟层（纯 C++，无 Qt）
    demo_scenario / ecology / life / faction / worldgen   —— 只产出数据
        ↓
快照层（纯 C++，无 Qt）
    gui::Simulation                                       —— 只出快照，不出控件
        ↓
绘制层
    EcologyView（QCanvasPainterWidget，GPU）                —— 上万精灵的自绘
    WorldView / PopulationChart（QWidget + QPainter）      —— 贴图与折线
        ↓
面板层（.ui / Qt Designer）
    主窗口、四个分组面板、选人对话框                     —— 拖拽改布局
        ↓
资产层（磁盘 + 文件监听，qrc 兜底）
    精灵、图集                                           —— 改完即生效
```

### 1. 快照层收口 ECS（先做这个）

`gui::Simulation` 补两个只读出口，GUI 就不再需要 ECS 头文件：

```cpp
/// 种群快照：位置、适应力、四项性状。视图画个体只认这个。
[[nodiscard]] std::vector<CreatureSnapshot> creatures() const;

/// 环境场的承载力，按格查。视图画底色只认这个。
[[nodiscard]] float capacity(gamev2::environment::CellIndex cell) const;
```

`entities()` 与 `environment()` 随后从公开接口里拿掉。收益不只是整洁：
快照层无 Qt 依赖，可以单测；界面再大改也不会波及 ECS。

### 2. 资产热重载

`SpriteBook` 改成先从磁盘目录读 `assets/sprites/characters`，用
`QFileSystemWatcher` 监听目录，变了就重载贴图；找不到目录时回落到 qrc。

- 改一张 PNG：保存即生效，不用编译、不用链接、不用重启。
- 发布形态仍然用 qrc（或 `windeployqt` 打包），不依赖工作副本。

### 3. 启动路径做成一条命令

- 世界地图**懒生成**：第一次切到「世界地图」页才生成那 1.85s，启动与
  「重开」都不再等它。
- 加启动参数：`--seed N --preset persist --speed fast --pick first`。
  `--pick first` 直接接管第一个候选，跳过选人弹窗。
- 结果：改完代码 → 重建 4s → 一条命令进可操作状态 ≈ 5s。

### 4. 面板搬 `.ui`

面板层（世界 / 玩家 / 种群 / 地图选格）与选人对话框的布局搬进 `.ui` 文件，
用 Designer 拖。C++ 只留逻辑与连接。

- 一个面板只有两三个控件、且不会再变 → 留代码里，别为 `.ui` 过度设计。
- 控件超过三个或预计还要加 → 进 `.ui`。`uic` 生成的 TU 单独编译，迭代只重编
  一个文件。

### 5. 顺手配一下 IDE

工程已经用 clang++，导出 `compile_commands.json` 即可让 clangd 索引整个仓库
（含 `include/`），跳转与补全立刻可用。这条几乎零成本。

## Qt 6.12 的大地图 2D 能力（2026-10-30 调研）

本机是 Qt 6.12.0 LTS。查过官方文档与发布博客后，结论是：**Qt 6.12 没有
「大地图 2D 像素游戏」的现成控件，但有一条 6.12 刚转正的 GPU 加速路线。**

### 没有官方 tile map 控件

Qt 6.12 不含任何 tilemap 模块（本机 `lib/cmake` 里没有；官方邮件列表里
Shawn Rutledge 也明说 "we don't have [a reusable tiling implementation]
yet"，他当时建议用 Qt Quick 的 `TableView` 做瓦片按需实例化）。Tiled 是第三方
的地图编辑器（本身用 Qt 写），不是控件。

### 三条候选路线

| 路线 | 相机/图层 | 性能 | 结论 |
| --- | --- | --- | --- |
| `QGraphicsView` | 自带（缩放/滚动/z 值/裁剪） | CPU 光栅，item 有开销 | 能用，但别新上 |
| Canvas Painter | 要自己写 | GPU | 6.12 转正，值得押注 |
| SceneGraph 自定义节点 | 自己写 | 最高 | 代价最大 |

**QGraphicsView/QGraphicsScene**（Qt Widgets 内置）自带相机、图层、视口裁剪，
当年就是给 2D 场景用的。但它基于 QPainter 做 CPU 光栅，而且官方态度明确：
"Graphics View has not been getting much attention in R&D for over a decade
already: only bug fixes"。没有正式废弃，但被算作"已完成"，官方建议新项目
避开。

### Canvas Painter：6.12 刚转正的那条路

`Qt Canvas Painter` 模块 6.11 引入（当时是技术预览），**6.12 正式转正**，
核心 API 进入兼容性承诺。

- **硬件加速的命令式 2D 绘制**，直接对着 QRhi 下命令（D3D12 / D3D11 /
  OpenGL / Vulkan / Metal），没有中间 QImage、没有 CPU 光栅，**也没有 CPU
  后端**。
- **Widget 与 Quick 都支持**：`QCanvasPainterWidget`（基于 `QRhiWidget`）可以
  塞进现有 QWidget 应用，别的控件继续走 QPainter 光栅；`QCanvasPainterItem`
  给 Qt Quick。这是"不迁窗口体系、只换地图控件"的路子。
- API 仿 HTML Canvas 2D（`beginPath` / `fill` / `stroke` / `drawImage` /
  pattern），比 QPainter 精简、抽象更少。
- **像素画友好**：`QCanvasPainter::ImageFlag::Nearest` 让图像插值用最近邻
  而不是线性；`RenderHint::Antialiasing = false` 关抗锯齿；`setAntialias()`
  还能按路径调抗锯齿量（只影响描边填充，不影响图像与文字）。
- 精灵图直接切：`drawImage` 的 9 参数形式切源矩形，`QCanvasImagePattern`
  做平铺瓦片，`QCanvasCustomBrush` + `qt_add_custom_brush_shaders` 上自定义
  着色器（描边、调色、体积光）。
- **官方基准**：普通 PC 约为 QPainter(OpenGL) 的 2 倍，低端安卓平板 5 倍、
  高端 10 倍；第三方在树莓派 4B 上实测重负载下 28fps vs 9fps，CPU 占用低
  37%。D3D12 明显快于 D3D11/OpenGL。
- **缺的东西**：滤镜（官方明说永远不做）、虚线描边、任意形状裁剪（只有矩形
  裁剪）、阴影（只有 box shadow）。

### 对本项目的取舍

**当时的结论是「别现在迁」，2026-10-30 改掉了：生态活体图已经迁到
`QCanvasPainterWidget`。**

当初列的三条顾虑，逐条核对后的实际情况：

| 当初的顾虑 | 现在的实际情况 |
| --- | --- |
| QPainter 光栅完全够用 | 够用，但生态视图已经从 6 千个白点变成 1.2 万个 16px 精灵，CPU 光栅的量级变了；而且后面要做相机、缩放、图层叠加，QPainter 没有 GPU 管线可接 |
| CanvasPainter 没有 CPU 后端，换机器可能画不出来 | **仍然成立**，是这次迁移实打实付的代价 |
| 绘制逻辑要重写，收益兑现不了 | 重写的是 `EcologyView` 一个控件；收益是给后面那几项需求留了地基 |

迁移的取舍与做法见 `doc/2026-10-29-qt-demo.md` 的「渲染后端」一节。要点：
静态场景（承载力底色 + 人群）烘进离屏画布缓存，每帧只贴一张纹理，再补画
玩家那几笔。

**世界地图视图不用换。** 那十个图层各自是一张 256×256 的 `QImage`，本来就
是「贴一张图」，CPU 光栅毫无压力。真要加相机与缩放，给它加一个
`drawImage(QRectF)` 的可见区裁剪 + 变换矩阵就行，几十行代码，用不上 GPU。

**剩下的触发信号**（出现任一条再评估）：

- 要做相机（滚动 / 缩放 / 平移）与多图层叠加；
- 生态视图要在 60fps 下跑，或个体数上到 5 万以上；
- 要加着色器特效（描边、调色、体积光）；
- 要出到移动端或低配设备——那时必须先确认目标平台有可用的 RHI 后端。

面板层搬 `.ui` 还是 QML，与地图层无关，两件事可以并行。

### 顺带：6.12 的 QML Hot Reload

Qt 6.12 首次提供官方的 **QML Hot Reload**（改 `.qml` 即时生效，不重编译）。
这让「面板层用 QML」的迭代成本比 6.11 之前低了不少——但它只解决面板层，
不解决地图层的重绘问题，因此不改变本文档「主干留在 QWidget」的结论。

## 为什么现在不上 QML

QML 的强项是**面板热重载**与**声明式布局**，正好是 `.ui` 能覆盖的那一层；
而这套 GUI 的重头戏是生态活体图——一帧上万个精灵的像素级自绘，QML 的
Item/Canvas 在这个量级上做不到又快又准，这部分无论如何要留在 C++。

- `QQuickWidget` 是性能与稳定性都出过问题的组件，不建议嵌。
- 干净的混合（`QQuickWindow` 外壳 + `QQuickPaintedItem` 承载生态视图）要把
  整个窗口体系迁到 Qt Quick，代价比拿到的多。
- 代价是**两套 UI 工具链**：`.ui`/uic 与 qmlcachegen/qmllint/qmlformat，
  外加 C++↔QML 的类型桥接（`QML_ELEMENT` 注册）。收益只覆盖面板层。

**重新评估的信号**（出现任一条再谈）：

- 面板数量超过 10 个，且 `.ui` 拼装也开始难读；
- 面板需要过渡动画、主题切换或 DPI 缩放策略；
- 需要同一套界面同时出桌面版与移动版。

到那时**只把面板层换成 QML**，重绘视图仍然留在 C++（可以是
`QQuickPaintedItem`，也可以是 SceneGraph 上的精灵图集批次）。真要给生态视图
做相机、缩放、光效，那是另一档需求，届时上 OpenGL/SceneGraph 批渲染，而不是
QML。

## 落地顺序

| 批次 | 内容 | 成本 | 收益 |
| --- | --- | --- | --- |
| 1 | 启动参数 + 世界地图懒生成 | 半天 | 迭代一圈 10s → 5s |
| 2 | 资产热重载 | 半天 | 美术迭代不等编译 |
| 3 | `Simulation` 收口 ECS | 1 天 | GUI 不再依赖 ECS，可单测 |
| 4 | 面板搬 `.ui`（按需逐个搬） | 每个面板 1–2 小时 | 改布局不写代码 |
| 5 | 触发式评估 QML 面板层 | — | 见上面的触发条件 |

批次 1–3 与已有功能不冲突，可以随时停在一半；4 是持续动作，不必一次搬完。
