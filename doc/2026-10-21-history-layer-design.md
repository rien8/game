## 0. 本文定位

### 0.1 这个模块是什么

**时序层**是把「已经生成好的世界」往前推演一段时间、产出**账**的模块。

第一刀的具体产物是**灵脉产权与开采台账**：从灵历 8300 年《脉律》重勘到
灵历 8914 年当代，六百年的开采、越采、枯竭，逐条脉记成账，并算出
**老配额与当代承载力的偏差**——也就是设定 §10.1「配额之争」的燃料。

它不是玩法。它不产生玩家操作，不产生胜负，不产生画面。

### 0.2 为什么不是第 18 个生成阶段

灵气层设计 §0.1 已经把边界画出来了：

> 这些都需要**时间推演**（渡劫要抽干方圆百里、兽潮要几十年蔓延、灵潮要
> 千年一轮），而不是一次性的空间生成。worldgen 产出的地形与灵气分布是它们的
> **初始条件**，不是它们本身。

时序层遵守同一条边界，且比灵气层多一条：**它不回写 worldgen 的任何字段**。

灵气层是「纯追加，不回写」（灵气层设计 §1.1）；时序层是「只读，不回写」。
两者的理由不同：灵气层追加的是**空间**上的结论，时序层追加的是**时间**上的
结论。两者都遵循「一个字段只有一个写入者」这条既有不变量。

### 0.3 本轮只做第一刀

本模块的完整形态很大（七宗兴衰、兽潮、渡劫、鬼修、魔修、王朝），但那些是
**后续纵切**。本轮只做一条纵切，且刻意把它做到能独立验证：

| 本轮做 | 本轮不做 |
|---|---|
| 七宗的脉持有格局（设定 §8.1） | 宗门之间的兼并、结盟、覆灭 |
| 《脉律》配额快照（8300） | 脉律的重勘与改版 |
| 六百年的逐年开采推进 | 兽潮、渡劫、鬼修、魔修 |
| 越采与枯竭的认领 | 越采者的动机与后果 |
| 老配额 vs 当代承载力的偏差表 | 政治事件与派系演化 |

纵切选择的理由：**偏差表是唯一能把设定 §10.1 的政治冲突变成可复算数字的
东西**。别的纵切都做不到这一点。

## 1. 与既有框架的关系

### 1.1 只读 worldgen，不回写

时序层读取 worldgen 的终态，**不修改 `World` 的任何字段**。输入清单见 §3.1。

这条边界有一个直接后果：**当代余额不能写进 `vein.reserve`**。worldgen 的
`reserve` 语义是「已被越采削减过的物理储量」（见 §3.2），而时序层要算的
「当代余额」比它更低——因为六百年里的**正常开采**没有体现在 worldgen 里。

所以时序层维护自己的余额字段（§2.2），两者并存：

- `vein.reserve` —— worldgen 的口径：物理储量，越采脉已被削 60%
- `QuotaEntry::balance` —— 时序层的口径：8300 年承载上限减去这六百年的全部开采

两者的差就是「正常开采量」。这个差是本模块最有价值的诊断量之一。

### 1.2 时序层的自有状态

时序层**不挂在 `World` 上**。它是一个独立的结构，由 worldgen 的终态构造：

```cpp
gamev2::history::Ledger build_ledger(const gamev2::world::World& world);
```

理由与既有设计 §8.1「世界不进 ECS」同源，但结论相反：

- worldgen 的产物是**空间**，空间是数据，适合进 `World`。
- 时序层的产物是**历史**，历史是一次性推演的结果，与空间无关。
  它不需要被 worldgen 的任何阶段读取，也不需要被任何阶段回写。

把 `Ledger` 塞进 `World` 会带来一个假的依赖方向：读代码的人会以为
worldgen 后面还有阶段要用它。

### 1.3 纪元

时序层的两个纪元：

| 名称 | 值 | 来源 |
|---|---|---|
| `epoch`（脉律纪元） | 8300 | 设定 §6.5：上次重勘在灵历 8300 年前后 |
| `now`（当代） | `world.params().spirit_year` | 默认 8914 |

两个值相减得到 **614 年**的推演跨度。

`epoch` 是常量，`now` 来自参数——参数允许把世界推到别的年份，台账的跨度会
跟着变，但起点恒在 8300（脉律只有这一版是既定的）。

## 2. 数据模型

### 2.1 为什么是台账而不是状态

「状态」是某一时刻的快照，「台账」是**一串有署名的增减**。

选择台账，理由有三：

1. **冲突需要过程，不是结论。** 「老配额不公」不是一个布尔值，是六百年里
   一笔笔开采累积出来的差。只存终态就丢了"谁在什么时候拿走了多少"。
2. **越采需要能指名。** 设定 §6.5 说「越采者，盟约有权力断其供给」——要执行
   这条，必须知道是哪一笔越采、哪一年、哪个宗。台账天然带这三个字段。
3. **可导出即可读。** 台账是文本友好的结构：它是**观察层的最小版**，
   不需要渲染就能被人读懂。这是《矮人要塞》那条教训（可读性不能拖到最后）
   在本项目里的第一处落地。

### 2.2 类型定义

```cpp
// include/gamev2/history/ledger.hpp
namespace gamev2::history {

/// 七宗。顺序固定：与设定 §8.1 的表格一致，索引即宗门编号。
enum class Sect : std::uint8_t
{
    taixuan,    ///< 太玄宗：龙脉 + 三条主脉，执掌盟约
    daxia,      ///< 丹霞谷：两条主脉
    hanjiang,   ///< 寒江剑府：一条阴脉
    wanshou,    ///< 万兽山：一条主脉
    qiangnang,  ///< 青囊谷：一条主脉
    tianji,     ///< 天机阁：无地，执历算
    jiuyou,     ///< 九幽宫：一条主脉，不登记
    unowned,    ///< 无主：散修与凡人共享的支脉
    count,
};

/// 一条脉的账。
struct QuotaEntry
{
    std::uint32_t vein = 0;
    Sect holder = Sect::unowned;
    VeinRank rank = VeinRank::none;

    /// 8300 年《脉律》核定的总量配额。天机阁历算的承载上限。
    std::uint32_t surveyed_total = 0;
    /// 8300 年核定的安全流速。
    std::uint32_t surveyed_rate = 0;

    /// 8300→8914 累计开采量。
    std::uint32_t extracted = 0;
    /// 其中越采的部分（认领 worldgen 的越采痕迹）。
    std::uint32_t overmined_amount = 0;
    /// 8914 当代余额 = surveyed_total − extracted。
    std::uint32_t balance = 0;

    /// 归零年（余额耗尽那年）。0 表示未枯竭。
    std::uint32_t depleted_year = 0;
    /// 该脉的脉律配额是否登记在册。九幽宫那条不登记。
    bool registered = true;
};

/// 一笔开采。
struct ExtractionEvent
{
    std::uint32_t vein = 0;
    std::uint32_t year = 0;
    std::uint32_t amount = 0;
    bool over_quota = false;
};

/// 一宗的汇总账。
struct SectLedger
{
    Sect sect = Sect::unowned;
    /// 名下脉的 8300 年配额总和。
    std::uint32_t quota_total = 0;
    /// 名下脉的 8300 年流速配额总和。
    std::uint32_t quota_rate = 0;
    /// 名下脉的当代余额总和。
    std::uint32_t current_total = 0;
    /// 名下累计开采量（≡ 配额 − 当代余额）。
    ///
    /// 恒 ≥ 0：配额封顶让越采不可能发生，余额永远不会低于 0，欠账这一侧
    /// 本账算不出来。
    std::int64_t deviation_total = 0;
    /// 流速偏差：核定流速按当代潮位折下来的差额，当代潮位高于 8300 时
    /// 为负。
    std::int64_t deviation_rate = 0;
    /// 累计越采量。
    std::uint32_t overmined_amount = 0;
};

/// 整本台账。
struct Ledger
{
    std::uint32_t epoch = 0;
    std::uint32_t now = 0;
    std::vector<QuotaEntry> veins;
    std::vector<ExtractionEvent> events;
    std::vector<SectLedger> sects;
    /// 未登记开采的总量（九幽宫那条脉 + 散修盗采）。
    std::uint32_t unregistered_extracted = 0;
};

}  // namespace gamev2::history
```

`VeinRank` 复用 `gamev2::world::VeinRank`，不另定义一套——灵脉品阶是同一个
概念，两个枚举各写一遍会让"这条是什么品阶"变成编译期歧义。

## 3. 第一刀规格

### 3.1 输入

只读 worldgen 的以下字段：

| 来源 | 字段 | 用途 |
|---|---|---|
| `world.veins` | `id` `rank` `reserve` `overmined` `eye` `element` | 脉的身份、品阶、物理储量、越采痕迹 |
| `world.eyes` | `vein` `node` `flow` `depleted` | 灵眼的流速与枯竭痕迹 |
| `world.ley_nodes` | `flow` | 重建枯眼**枯竭前**的流速 |
| `world.cave_heavens` | `upkeep` | 洞天年耗（红线 2） |
| `world.spirit_tide` | `year` `phase` `level` | 当代潮位 |
| `world.params()` | `spirit_year` | 当代纪元 |

**不用** `land_type`、`scar_kind`、`domain_grade`：第一刀不判地貌，不认疤痕。
疤痕是「事件留下的痕迹」，不是「账」。

### 3.2 8300 快照：脉律基数的推定

《脉律》是 8300 年核定的，所以台账需要一个**8300 年的数**。worldgen 只给
当代的数，两者要接上。

**物理储量**：worldgen 的 `vein.reserve` 已经是**扣除越采之后**的值——
`mark_overmined()` 把越采脉的储量乘 40%（`kOverminePenalty = 60`）。所以：

```
非越采脉： surveyed_total = reserve
越采脉：   surveyed_total ∈ [ ceil(reserve × 100/40),  ceil((reserve+1) × 100/40) )   // 反推区间
```

反推不唯一，因为 `reserve = floor(original × 40 / 100)` 是整除。给定 `reserve`，
原值有三个或两个候选（取决于 reserve 的奇偶：偶数时 3 个，奇数时 2 个）。

**区间宽度是 2 或 3，不是恒为 3**。实现取的是排他上界
`ceil((reserve+1) × 100/40)` 而不是固定 `+3`——固定 `+3` 在奇数 reserve 上
会多报一格。宽度上界仍是 3，所以下文的「±3 噪声底」按最坏情况取用，
结论不变。

**这个 ±3 的区间不是缺陷，是本模块的设计资产**：它就是**天机阁历算的误差**。
设定 §6.5 说脉律「每二百年重勘一次」，六百年间没人重算；算的时候又是按
巅峰期的数算的。误差 + 时差 + 开采，三者叠加，就是「老配额早已不公」的
物理来源。

**安全流速**：枯眼的 `eye.flow` 被 `mark_depleted_eyes()` 置零，但原始吞吐
还在 `world.ley_nodes[eye.node].flow` 里（阶段 13 就是从那儿取的）。
所以 8300 年的流速可以重建：

```
surveyed_rate = world.ley_nodes[eye.node].flow
```

非枯竭眼的 `eye.flow` 本来就等于它，直接用。

### 3.3 持有格局与配额

**持有格局是设定给定的，不是推演出来的。** 设定 §8.1 的表格是硬事实：

| 宗门 | 名下脉 |
|---|---|
| 太玄宗 | 龙脉 + 三条主脉 |
| 丹霞谷 | 两条主脉 |
| 寒江剑府 | 一条阴脉（主脉级） |
| 万兽山 | 一条主脉 |
| 青囊谷 | 一条主脉 |
| 九幽宫 | 一条主脉（**不登记**） |
| 天机阁 | 无地 |
| 无主 | 全部支脉（散修与凡人共享） |

合计 3 + 2 + 1 + 1 + 1 + 1 = 9 条主脉，与设定「天下九条主脉」一致。

**分配规则**（确定性，不随机——随机会让设定失效）：

1. 龙脉（`rank == dragon`，恒 1 条）→ 太玄宗。
2. 主脉按 `reserve` 降序排，取前九条：
   - 第 1、2、3 条 → 太玄宗
   - 第 4、5 条 → 丹霞谷
   - 第 6 条 → 寒江剑府
   - 第 7 条 → 万兽山
   - 第 8 条 → 青囊谷
   - 第 9 条 → 九幽宫（`registered = false`）
3. **寒江剑府的阴脉**：设定说它握的是「一条阴脉（采出即衰）」，即地貌为阴地
   的那条。判定口径：取 `vein_id == 该脉编号` 的格，看其中有没有
   `land_type == LandType::yin` 的——有则这条是阴脉。若第 6 条不是阴地，
   则在主脉里**另找一条阴地脉**给寒江；找不到就按序取第 6 条，并把这件事
   记进诊断（§5）。
4. 支脉（`rank == branch`，约 40 条）→ `unowned`（散修与凡人共享池）。
5. 荒脉（`rank == barren`）无灵眼、不可采 → 不进台账，只计数。

**配额**：一条脉一个持有者，所以持有者拿这条脉的全额配额：

```
quota_total(脉) = surveyed_total(脉)
quota_rate(脉)  = surveyed_rate(脉)
```

`QuotaEntry::quota_total` 就是 `surveyed_total`；`SectLedger` 做汇总。

### 3.4 逐年推进

从 `epoch`（8300）到 `now`（8914），逐年推演。每年对每条可采的脉：

```
1. 当年潮位 level = compute_spirit_tide(year).level      // 0..255
2. 有效流速 = surveyed_rate × level / 255
                // 物理吞吐不随潮位变（阶段 13 的注释），但环境浓度决定
                // 修士能抽出多少。谷底期潮位 33 ≈ 13%，灵潮期末 255。
3. 当年上限 = min(有效流速, 脉余额)
4. 正常开采 = min(当年上限, 该脉剩余配额)
5. 越采（若该年被认领为越采年）= 额外开采量
6. 余额 -= 正常开采 + 越采；extracted += 正常开采 + 越采
```

**配额的作用**：设定 §6.5「采至配额上限须停采，待灵脉自行恢复」。所以正常
开采被 `surveys_total − extracted` 卡住——采满了就停。这正是「老配额」
发挥作用的地方：**在潮位低的年份，配额根本用不掉**。

**潮位的作用**：这是本模块最重要的物理事实。灵历 8300 恰好是**上一轮灵潮的
峰值年**——`compute_spirit_tide(8300)`：`cycle = 7`（0 起，即第八轮）、
`phase = tide`、`year_in_phase = 299`、`peak = 110`，而当年 `level` 恰等于
`peak`（同 `compute_spirit_tide(9300)` 的结构）。

也就是说：**脉律的基数是在天下灵气最充沛的一年编的**。六百年后（灵历 8914，
谷底期第 113 年）回看当代承载力，`level` 只有 33——约三成。

这个结构性偏差**在没有人偷采的情况下就已经存在**。

设定 §8.2 说魔修「把一个真问题推到极端的答案」——真问题就是这个。台账把它
算出来。

### 3.5 越采与枯竭的认领

worldgen 已经标好了当代的越采与枯竭痕迹（阶段 13 的 `overmined` 与
`eye.depleted`）。时序层**不重新发明历史**，它给这些痕迹配上账：

**越采的认领**：

- 对每条 `overmined == true` 的脉，越采总量 = `surveyed_total − reserve`
  （恒等式：越采削掉的那部分）。
- **越采发生在哪一年**：由 `vein_id` 派生的确定性抽样选出（见 §4），
  落在 8300..8914 之间。年份必须早于当代，且不能太早——脉律是 8300 编的，
  越采案若发生在 8300 之前，脉律不会不管。所以采样区间取 [8301, 8914]。
- **谁越采**：该脉的持有者（`holder`）。九幽宫那条脉不登记，它的越采计入
  `unregistered_extracted`。

**枯竭的认领**：

- 对每条 `eye.depleted == true` 的脉，余额在某一年归零，归零年记入
  `depleted_year`，之后不再开采。
- 归零年同样由确定性抽样选出，但必须满足：归零年 **不早于** 该脉的越采年
  （有因才有果），且 **不晚于** `now`。

**认领的失败模式**：如果某条脉的越采量与归零年在推演中对不上（例如越采年
采光了整条脉，但归零年被采到更早），说明认领不自洽。处理办法见 §5。

### 3.6 偏差表：老配额 vs 当代承载力

台账的核心输出。三层：

**第一层 · 脉级**

```
偏差(脉) = quota_total(脉) − balance(脉)
```

这是该脉 8300 年以来被采走的量。**它不会是负的**：越采那一笔按当年余额
封顶，余额永远不低于 0，所以「已经被采穿」这一侧本账算不出来。

**第二层 · 宗级**

```
SectLedger::deviation_total = Σ_{v ∈ 名下} (quota_total(v) − balance(v))
```

这一层就是「谁采走得多」的答案，也就是各宗累计开采量。

**第三层 · 口径差**（本模块的招牌输出）

把偏差拆成两部分：

```
结构性偏差 = Σ (surveyed_total × (1 − 当代潮位系数 / 8300年潮位系数))
越采偏差   = Σ overmined_amount
```

第一部分是**口径差**——8300 按峰值口径编、8914 按谷底口径看，与谁都没偷
采无关。第二部分是**人为差**——谁真的多采了。

**这一层区分了三种立场**：

| 立场 | 口径差 | 越采差 | 诉求 |
|---|---|---|---|
| 正派守律派 | 承认 | 追究 | 维持脉律，严惩越采 |
| 太玄宗（重分派） | 主张按当代承载力重分 | 自己是否越采由账说话 | 重新分配 |
| 魔修（取尽派） | 无所谓 | 无所谓 | 抽干炼血 |

设定 §8.1 说太玄宗「霸权，但受脉律约束」，§8.2 说魔修「把一个真问题推到
极端的答案」。**台账让"谁有理"变成可复算的数**，而不是剧本安排。

### 3.7 守恒对账

三条恒等式，全部可断言：

1. **逐年**：任何时刻 `balance ≥ 0`，且
   `balance(v, y) = balance(v, y−1) − Σ 当年开采`。
2. **跨层**：`balance(v, 8914) = surveyed_total(v) − extracted(v)`。
3. **与 worldgen 对账**：`reserve(v) − balance(v, 8914) = 正常开采量 ≥ 0`。
   越采脉的 `reserve` 已被 worldgen 削过，所以这条恒等式对越采脉与正常脉
   都成立——它验证的是**台账没有把越采重复计一次**。

第 3 条是本模块与 worldgen 之间的接缝。差值应当为正：正常开采只会让余额
比 worldgen 的物理储量更低。若出现负值，说明台账把越采又扣了一次。

## 4. 参数与随机流

时序层的随机性只有一处：**越采年与枯竭年的抽样**。

**随机流**：沿用 worldgen 的 `stage_seed(seed, stream)` 模式，新增一个
`Stream` 枚举值 `Stream::ledger`。理由与既有设计一致——每个阶段一条独立的
随机流，改动一个阶段不会波及其他阶段的产物。

注意 `Stream` 定义在 `include/gamev2/world/enums.hpp`，而紧随其后的
`static_assert` 是**流号登记表**：新增一条流必须同改那份清单，否则编译不过。
这是既有代码里已经写明的规矩（`enums.hpp` 的注释原文：「新增一条流必须
同改」）。

**抽样规则**：

- 越采年：`Pcg32(stage_seed(ledger_seed, vein_id))` 的第一次取值映射到
  `[8301, 8914]`。
- 枯竭年：同上，但用不同的 salt，且必须晚于该脉的越采年。

**为什么用 `vein_id` 而不是别的键**：灵脉的身份是 `id`，与名次无关
（阶段 13 的 `segment_seed` 用的是「通道号 + 段首下标」，正是为此）。
所以同一条脉在任何世界里都得到同一个抽取结果——这与「同一条脉在同一段
历史里经历同样的事」一致。

**不接受为随机的地方**：持有格局（§3.3）、配额（§3.3）、潮位
（`compute_spirit_tide`，纯函数，在 `spirit_tables.hpp` 里是 constexpr）。
这些必须是确定的，否则设定失效、测试无法断言。

## 5. 错误处理

时序层**不引入新的失败模式**，沿用灵气层 §5 的口径：退化不是错误，由诊断
量报出。

| 情况 | 处理 |
|---|---|
| 世界没有灵脉 | 返回空台账，`veins` 为空 |
| 主脉不足 9 条 | 按实有条数分配，多出来的宗拿到零条脉 |
| 找不到阴地主脉给寒江剑府 | 按序分配，并在诊断里报一条 |
| 越采年采样落在枯竭年之后 | 把越采年拉到枯竭年之前（必要时同年） |
| 余额在某年归零但 worldgen 没标枯竭 | 记一条诊断，台账按归零处理（余额为 0 不会再采） |
| worldgen 标了枯竭但推演中余额没归零 | 记一条诊断，并把归零年设为 `now` |
| `now < epoch` | 台账为空，跨度为负 |
| 推演跨度超过上限（100000 年） | 按「没有推演」处理：余额停在基数上，记一条诊断 |

诊断量沿用 worldgen 的做法：单独一个 `LedgerDiagnostics` 结构，由调用方
决定要不要打印。demo 程序负责打印。

## 8. 已知限制与风险

### 8.1 持有格局是设定给定的，不是涌现的

第一刀直接采用设定 §8.1 的表格。这是**有意的**：设定把这些当硬事实，而
本刀的目标是算清「这个格局在六百年后还成不成立」，不是「这个格局怎么来的」。

**代价**：台账不能回答「太玄宗是怎么拿到龙脉的」。兼并史是后续纵切。

### 8.2 8300 年的基数是反推的，带 ±3 区间

整除导致反推不唯一（§3.2）。本设计**保留区间而不取中值**，因为误差本身
是设定的一部分。

**代价**：偏差表里有一个 ±3 的噪声底。脉级偏差小于 3 时不可断言。

### 8.3 worldgen 的 `reserve` 口径在越采脉与正常脉之间不一致

越采脉的 `reserve` 已被削 40%，正常脉的没有（因为 worldgen 不模拟正常
开采）。这是一个**继承下来的口径债**。

**影响**：台账必须把 `reserve` 当成「已扣越采的物理上限」来读，并在自己这边
再扣正常开采。§3.7 第 3 条恒等式就是专门盯这个的。

**根治办法**（本轮不做）：把越采的 40% 削减从 `reserve` 里拿掉，改用独立
字段 `overmined_loss`，让 `reserve` 恒等于物理上限。代价是 `reserve` 是
品阶排名键（`reserve × stability`），改动会重排所有脉的品阶——现有实测表
全部失效，应当作为一次独立的重标定任务做。

### 8.4 潮位系数是拍脑袋的一阶近似

「有效流速 = 物理吞吐 × 潮位系数」是一条假设。物理吞吐确实不随潮位变
（阶段 13 的注释），但修士能抽出多少与浓度的关系是平方、还是三次方，
没有依据。

**缓解**：台账的结论对系数的**取值**不敏感（只要是单调的），只对**潮位
在两个纪元的比值**敏感。而那个比值是 `compute_spirit_tide` 给的确定值。
系数只影响绝对量，不影响偏差的符号与相对大小。

### 8.5 未登记开采只有总量，没有细节

九幽宫那条脉与散修的盗采，第一刀只记总量（`unregistered_extracted`），
不记年份与次数。

**代价**：无法回答「九幽宫是哪一年开始盗采的」。

### 8.6 逐年推进是 614 次循环，成本可忽略

614 年 × 约 50 条脉 = 三万次内层计算。**不需要按年预计算或缓存**。

## 9. 未决问题

1. **寒江剑府的阴脉找不到怎么办？** 本设计取「按序取第 6 条并报诊断」。
   另一种取法是「没有阴脉就不给寒江脉，它的偏差归入无主」——后者更忠于
   设定，但会让九主脉的分配出现空缺，需要额外规则。
2. **散修与凡人共享池要不要按潮位分成"丰年/荒年"两档？** 本设计取单一
   规则（无主脉按潮位比例开采，不设配额上限）。
3. **越采要不要有"被发现"的延迟？** 本设计取「越采当年即入账，不设发现
   延迟」——发现延迟属于司法流程，不属于账。
4. **台账要不要覆盖灵潮期以外的时间？** 614 年已经跨了衰退期、谷底期、
   灵潮期三段。再往前推到 7800 年（上一轮脉律）会需要第二份配额表。
   本设计取「只推演一版脉律」。
